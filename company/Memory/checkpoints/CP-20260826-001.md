# CP-20260826-001 — Nuovo orchestration-layer innestato in 11-APEX-7-CORE come canone (Fase 1) — Neri

**Chi**: Emperator Agent (sessione Neri)
**Cosa**: Neri ha portato un progetto di orchestrazione costruito in Antigravity IDE
(`W0→W13`: builder swarm, plan memory BM25, contratti JSON Schema, adapter Postgres,
governance OPA, bridge RuFlo pinnato, chaos/recovery, API+worker, PRR). Chiesto
esplicitamente come trattarlo rispetto al motore canonico esistente (ADR-010/011
vietano nuove linee di orchestrazione fuori da `11-APEX-7-CORE`) — Neri ha scelto
**"sostituisce il canone"**.

**Fatto**:
- Copiato in `company/Ecosistemi/11-APEX-7-CORE/orchestration-layer/`.
- Primo tentativo di archiviare il vecchio `orchestrator/`+`orchestration/` ha rotto
  7 test — sono ancora agganciati in produzione a `calc/engine.py`,
  `arena_generator.py`, `main.py`. Ripristinati subito (ADR-003).
- Trovato e disinnescato un problema d'ambiente reale: install pip editable globale
  di `orchestration-layer` (residuo del build Antigravity) collideva col nome
  `orchestrator` del motore attivo, rompendo i suoi test su qualunque sessione con
  quell'editable install presente. Disinstallato.
- Verificato in esecuzione reale: motore vecchio 92/92 verdi (invariato), nuovo
  motore 148 verdi + 11 skip (richiedono Postgres/OPA/RuFlo reali).
- ADR-012 scritto con dettaglio completo + nota ⚠️ in testa al README di
  `11-APEX-7-CORE`.

**Non fatto (dichiarato, non nascosto)**: nessun consumatore reale migrato al nuovo
motore, bridge RuFlo non certificato in questo ambiente (serve `npm install` +
certificazione), nessuna decisione presa sull'ordine di migrazione.

**RIPRESA DA**: vedi ADR-012 §RIPRESA DA — (1) ordine migrazione consumatori,
(2) certificazione RuFlo bridge, (3) solo dopo: archiviare il motore legacy.

Dettaglio completo: [ADR-012](../decisions/ADR-012-orchestration-layer-canonico.md).
