## Lezioni
- **Il rischio reale dei checkpoint "lavoro concorrente sullo stesso PC" non è il conflitto di
  merge testuale (quello lo segnala git) — è la cancellazione silenziosa di contenuto di terzi
  durante la risoluzione automatica delle parti *non* in conflitto.** Un `git rebase --continue`
  dopo aver risolto un solo file può comunque portare con sé un indice sporco lasciato da
  un'operazione concorrente (stash/pop di un altro processo git sullo stesso working directory).
  **Prassi da tenere:** dopo ogni rebase con conflitto, fare `git diff <commit-origine-noto-buono>
  HEAD --stat` su tutto il repo (non solo sui file toccati) prima di pushare — è l'unico modo per
  accorgersi di una cancellazione silenziosa di file che il proprio conflitto non menzionava.
- Quando due sessioni lavorano sullo stesso identico obiettivo in parallelo (qui: arricchire gli
  `AGENTE.md` con il Python incorporato), meglio verificare lo stato su disco prima di ogni
  scrittura (`grep -c '```python'` per file) che tentare di "vincere" la corsa — il risultato
  finale desiderato è lo stesso indipendentemente da chi scrive per primo.
