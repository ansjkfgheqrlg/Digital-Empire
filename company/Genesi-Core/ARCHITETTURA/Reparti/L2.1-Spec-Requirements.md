# L2.1 — SPEC & REQUIREMENTS
## Organo: ARCHITETTURA (Genesi Core)

## Missione
Trasforma una richiesta grezza (`{tipo, scopo, vincoli, committente}`) in una **spec precisa e
non ambigua** prima che chiunque disegni o costruisca. Confine netto: L2.1 definisce *cosa* va
fatto e *perché* (requisiti, acceptance, out-of-scope) — NON la struttura (quella è L2.2
BLUEPRINT) e NON il contenuto (quello è la FORGE). In termini SPARC L2.1 possiede la fase
**Specification**: nessuno passa a Pseudocode/Architecture senza una spec approvata qui.

## Team (agenti)
| id | ruolo | tier |
|---|---|---|
| `arch-spec-writer` | Specification Writer: richiesta → spec con acceptance/out-of-scope | sonnet |
| `arch-director` | conductor: riceve la richiesta, instrada a L2.1, valida la spec prima del passaggio | opus |
| `arch-pattern-scout` | (in prestito dalla Guild) cerca spec/requisiti simili già scritti | haiku |

## Workflow di competenza
- **Fase Specification di WF-ARCH-DESIGN** — primo nodo dopo l'intake: la richiesta diventa spec.
- Alimenta **WF-STRUCT-VALIDATE**: l'acceptance della spec è il riferimento contro cui il
  validator (L2.4) misura "completo/incompleto".
- Per ecosistemi interi: produce la spec di mandato che apre **WF-ECOSYSTEM-DESIGN** (L2.5).

## Funzioni
1. **Intake disambiguato** — normalizza la richiesta: qual è la FORMA richiesta (skill/agente/
   team/principio/stile/workflow/documento/reparto/ecosistema)? qual è lo scopo a una frase?
2. **Requisiti** — lista numerata di requisiti funzionali + vincoli (tecnici, di tempo, di brand).
3. **Acceptance criteria** — condizioni misurabili di "fatto": ogni criterio è verificabile.
4. **Out-of-scope esplicito** — cosa NON fa parte, per impedire scope-creep a valle (FORGE).
5. **Dipendenze** — cosa serve già esistente (motori, schemi, altri artefatti) perché funzioni.
6. **Quality score della spec** — punteggio 0-100 (stile `prd-architect-os`): <60 → blocca, rimanda.

## Handoff Contract (Input → Output → Gate)
- **Input:** `{ tipo, scopo, vincoli, committente }` da `arch-director`.
- **Output:** `spec = { forma, scopo_1frase, requisiti[], acceptance[], out_of_scope[],
  dipendenze[], quality_score }` salvato in `architettura/blueprint/<id>/spec`.
- **Gate:** `quality_score ≥ 60` E acceptance non vuoto E out-of-scope non vuoto. Altrimenti
  la spec torna ad `arch-spec-writer` con la lista dei buchi (mai passare una spec sotto soglia).

## Flusso interno (passi reali)
```
richiesta {tipo,scopo,vincoli}
  → arch-spec-writer: classifica la FORMA (verifica vs §1 dossier: leggera o pesante?)
  → arch-pattern-scout (parallelo): esiste già una spec simile? la riusa come base
  → arch-spec-writer: scrive requisiti → acceptance → out-of-scope → dipendenze
  → arch-spec-writer: calcola quality_score (intake + acceptance + chiarezza)
  → score < 60 ? → rimanda con buchi : → emette spec
  → arch-director: valida e inoltra a L2.2 (BLUEPRINT) + L2.3 (carica schema canonico)
Output: spec validata → architettura/blueprint/<id>/spec
```

## shared_state / memoria (namespace architettura/...)
- `architettura/blueprint/<id>/spec` — la spec di ogni design, ricostruibile a freddo (test amnesia).
- `architettura/pattern` (lettura) — spec/requisiti riusabili individuati dal pattern-scout.
- `architettura/validazioni` (relay) — l'acceptance viene letta da L2.4 come riferimento del gate.
- Motore reale: `agent-specification` (SPARC Phase 1) + `prd-architect-os` (quality score, intake).

## Gate / KPI
| KPI | Target |
|---|---|
| Spec con quality_score ≥ 60 prima del passaggio a L2.2 | 100% |
| Spec con acceptance criteria misurabili (non vaghi) | 100% |
| Spec con out-of-scope esplicito | 100% |
| Forma classificata correttamente (leggera vs pesante) | rivista in RETRO se errata |
| Richieste rimandate per ambiguità (intake fallito) | tracciate, trend ↓ |
