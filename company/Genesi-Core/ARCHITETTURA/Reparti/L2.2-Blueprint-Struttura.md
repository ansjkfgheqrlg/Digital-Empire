# L2.2 — BLUEPRINT & STRUTTURA
## Organo: ARCHITETTURA (Genesi Core)

## Missione
Trasforma la spec approvata (da L2.1) nella **struttura millimetrica** dell'artefatto: file,
sezioni, I/O concreto, handoff, progressive disclosure. È il cuore disegnativo dell'organo.
Confine netto: L2.2 disegna lo *scheletro* — dove va ogni cosa, quali campi, quali sezioni —
ma NON scrive il contenuto che riempirà quelle sezioni (lo fa la FORGE). In SPARC: possiede
**Pseudocode → Architecture**. La fabbrica non inventa strutture: le chiede qui.

## Team (agenti)
| id | ruolo | tier |
|---|---|---|
| `arch-blueprint` | Architetto-Struttura: spec → struttura millimetrica (file/sezioni/I/O) | opus |
| `arch-schema-keeper` | (da L2.3) fornisce lo schema canonico della forma su cui modellare | sonnet |
| `arch-director` | conductor: sintetizza il blueprint finale e lo inoltra al gate | opus |

## Workflow di competenza
- **Nodo centrale di WF-ARCH-DESIGN** — riceve `spec + schema_canonico`, emette il `blueprint`.
- Pre-condizione di **WF-STRUCT-VALIDATE** (L2.4): il blueprint è ciò che il struct-gate misura.
- Per ecosistemi: collabora con L2.5, che usa lo stesso motore su scala org L1→L5.

## Funzioni
1. **Mappatura schema → istanza** — prende lo schema canonico (L2.3) e lo istanzia per *questo*
   artefatto: riempie i "buchi strutturali" con la struttura concreta, non con il contenuto.
2. **Struttura file** — quali file/cartelle nascono, con quale naming Title-Case fisso.
3. **Sezioni & ordine** — per ogni file, le sezioni obbligatorie e il loro ordine (es. SKILL.md:
   frontmatter → kernel ≤500 righe → references/; agente: identità → I/O → logica → KPI).
4. **I/O concreto** — schema JSON di input/output e degli handoff fra le parti dell'artefatto.
5. **Progressive disclosure** — cosa sta nel kernel vs cosa va nelle references (forme skill/doc).
6. **Annotazione "da-riempire"** — ogni sezione marca cosa la FORGE deve produrre dentro di essa.

## Handoff Contract (Input → Output → Gate)
- **Input:** `spec` (L2.1) + `schema_canonico` (L2.3) + eventuali `pattern` riusabili (Guild).
- **Output:** `blueprint = { struttura_file[], sezioni_per_file{}, io_json{}, handoff[],
  progressive_disclosure{}, da_riempire[] }` in `architettura/blueprint/<id>/blueprint`.
- **Gate:** ogni sezione obbligatoria dello schema canonico è presente nel blueprint (verificato
  da L2.4). Blueprint non validato → NON si passa alla FORGE (regola di blocco del dossier §4).

## Flusso interno (passi reali)
```
spec (L2.1) + schema_canonico (L2.3)
  → arch-blueprint: mappa ogni elemento dello schema sulla forma concreta richiesta
  → arch-blueprint: definisce struttura file + naming Title-Case fisso (lezione collisione Win)
  → arch-blueprint: per ogni file → sezioni obbligatorie + ordine + I/O JSON
  → arch-blueprint: marca le sezioni "da_riempire" (confine: struttura sì, contenuto no)
  → arch-director: sintetizza blueprint → invia a L2.4 (struct-gate) + L2.4 contradiction
  → gate PASS ? → HANDOFF a FORGE : → torna ad arch-blueprint con i buchi
Output: blueprint validato → architettura/blueprint/<id>/blueprint
```

## shared_state / memoria (namespace architettura/...)
- `architettura/blueprint/<id>/blueprint` — il blueprint completo, ricostruibile a freddo.
- `architettura/schemi` (lettura) — gli schemi canonici versionati da cui si parte.
- `architettura/pattern` (lettura) — pattern strutturali riusabili dalla Guild (anti-reinvenzione).
- Motore reale: `architect-agent` + `agent-architecture` (SPARC Phase 3, structure before code).

## Gate / KPI
| KPI | Target |
|---|---|
| Sezioni obbligatorie dello schema presenti nel blueprint | 100% |

| Naming Title-Case fisso, 0 collisioni maiuscolo/minuscolo | 0 violazioni |
